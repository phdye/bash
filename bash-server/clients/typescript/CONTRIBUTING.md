## Development Setup

### Prerequisites

- Node.js 16+ (20 LTS recommended)
- npm 8+
- bash-server built and available in PATH (for integration tests)
- Git

### Getting Started

```bash
# Clone the repository
git clone https://github.com/your-org/bash.git
cd bash/bash-server/clients/typescript

# Install dependencies
npm install

# Verify everything works
npm test

# Build
npm run build

# Type-check without emitting
npx tsc --noEmit
```

### Development Workflow

```bash
# 1. Create a feature branch
git checkout -b feature/my-feature

# 2. Make your changes in src/

# 3. Run tests continuously during development
npx jest --watch

# 4. Type-check
npx tsc --noEmit

# 5. Run full test suite
npm test

# 6. Build to verify compilation
npm run build

# 7. Commit and push
git add src/ tests/
git commit -m "Add my feature"
git push origin feature/my-feature
```

### Key Rules

- **Never modify `dist/`** &mdash; it is generated by `npm run build`.
- **Never commit `node_modules/`** &mdash; it is in `.gitignore`.
- **All source in `src/`** &mdash; TypeScript only, no JavaScript.
- **All tests in `tests/`** &mdash; mirror the `src/` structure.
- **Public API only through `index.ts`** &mdash; consumers should not import
  from internal paths like `bashclient/dist/protocol`.

## TypeScript Conventions

### Strict Mode

The project uses `"strict": true` in `tsconfig.json`. All code must pass
strict type checking. This means:

- No implicit `any` types.
- Strict null checks enabled.
- No unused locals or parameters (prefix with `_` if intentionally unused).
- Strict property initialization in classes.

### Naming Conventions

| Element          | Convention    | Example                    |
|------------------|---------------|----------------------------|
| Classes          | PascalCase    | `BashClient`, `FrameReader` |
| Interfaces       | PascalCase    | `EvalResult`, `VarInfo`     |
| Methods          | camelCase     | `getVar`, `setAlias`        |
| Properties       | camelCase     | `socketPath`, `exitCode`    |
| Constants        | UPPER_SNAKE   | `CHAN_CONTROL`, `TOKEN_HEXLEN` |
| Local variables  | camelCase     | `lineBuffer`, `pendingCount` |
| Private members  | camelCase     | `private queue`, `private closed` |
| Type parameters  | Single letter | `T`, `R`                    |
| Files            | kebab-case or camelCase | `control.ts`, `types.ts` |

### Interface Design

- Use `interface` for data shapes (not `type` aliases for objects).
- Use `type` for unions, intersections, and utility types.
- Export interfaces that consumers need from `index.ts`.
- Keep interfaces minimal &mdash; only include fields that are always present.
- Use optional fields (`?`) for fields that may be absent.

```typescript
// Good: clear interface with required and optional fields
interface Breakpoint {
  id: number;
  kind: string;
  enabled: boolean;
  hit_count: number;
  pattern?: string;     // Optional: only for command/function breakpoints
  line?: number;        // Optional: only for line breakpoints
  condition?: string;   // Optional: conditional breakpoints
}
```

### Wire Format Field Names

Interface fields that map to JSON wire protocol use **snake_case** to match
the server's JSON format. This avoids unnecessary field name translation:

```typescript
// Matches wire format directly
interface EvalResult {
  stdout: string;
  stderr: string;
  exit_code: number;    // snake_case matches JSON from server
}
```

Method names use **camelCase** per TypeScript convention:

```typescript
// camelCase for methods
client.state.getVar("HOME");
client.debug.addBreakpoint({ kind: "command", pattern: "*" });
client.pty.writeInput("ls\n");
```

### Error Handling

- Always throw typed errors from `errors.ts`.
- Never throw plain strings or generic `Error` instances.
- Set `this.name` in error constructors for proper `instanceof` behavior.
- Include enough context in error messages for debugging.

```typescript
// Good
throw new ProtocolError(`Unexpected message type: ${message.type}`);

// Bad
throw new Error("bad message");
throw "something went wrong";
```

### Async Patterns

- All I/O methods return `Promise<T>`.
- Use `async/await` internally (not raw Promise constructors) where possible.
- Event callbacks are synchronous (no `async` handlers).
- Always handle cleanup in `finally` blocks.

## Code Style

### Formatting

- **Indentation**: 2 spaces.
- **Semicolons**: Required.
- **Quotes**: Double quotes for strings.
- **Trailing commas**: Yes, in multi-line constructs.
- **Line length**: 100 characters soft limit.
- **Braces**: Same-line opening brace (K&R style).

### Imports

Order imports as follows:

1. Node.js built-in modules (`net`, `fs`, `child_process`)
2. Internal modules (relative imports)
3. Type-only imports last

```typescript
import * as net from "net";
import * as fs from "fs";

import { Transport } from "./transport";
import { encodeMessage, decodeMessage } from "./protocol";
import { TransportError } from "./errors";

import type { Message, EvalResult } from "./types";
```

### Comments

- Use `/** JSDoc */` for public API methods and classes.
- Use `//` for inline implementation notes.
- Do not over-comment obvious code.
- Document "why" not "what".

```typescript
/**
 * Execute a bash command and return the result.
 *
 * @param command - The bash command to execute.
 * @param options - Optional settings (timeout).
 * @returns The command's stdout, stderr, and exit code.
 * @throws {TimeoutError} If the command exceeds the timeout.
 * @throws {TransportError} If the connection is lost.
 */
async eval(command: string, options?: EvalOptions): Promise<EvalResult> {
  // ...
}
```

## Testing

### Test Framework

We use **Jest** with **ts-jest**. All tests are TypeScript files in `tests/`.

### Running Tests

```bash
# All tests
npm test

# Specific file
npx jest tests/protocol.test.ts

# Pattern match
npx jest --testNamePattern="FrameReader"

# Watch mode
npx jest --watch

# Coverage
npm run test:coverage
```

### Test File Naming

Each source module has a corresponding test file:

| Source                   | Test                           |
|--------------------------|--------------------------------|
| `src/client.ts`          | `tests/client.test.ts`         |
| `src/protocol.ts`        | `tests/protocol.test.ts`       |
| `src/transport.ts`       | `tests/transport.test.ts`      |
| `src/errors.ts`          | `tests/errors.test.ts`         |
| `src/channels/control.ts`| `tests/channels/control.test.ts`|

### Writing Tests

#### Test Structure

```typescript
describe("ModuleName", () => {
  describe("methodName", () => {
    it("should do the expected thing", () => {
      // Arrange
      const input = ...;

      // Act
      const result = someFunction(input);

      // Assert
      expect(result).toBe(expected);
    });

    it("should throw on invalid input", () => {
      expect(() => someFunction(null)).toThrow(SomeError);
    });
  });
});
```

#### Mocking

Use the `MockTransport` pattern from [ARCHITECTURE.md](ARCHITECTURE.md) for
unit tests. Do not mock internal methods &mdash; mock at the transport boundary.

#### Async Tests

```typescript
it("should eval a command", async () => {
  // Setup mock to respond
  setTimeout(() => {
    mockTransport.simulateData('{"ch":1,"type":"complete","stdout":"ok\\n","stderr":"","exit_code":0}\n');
  }, 10);

  const result = await client.command.eval("echo ok");
  expect(result.stdout).toBe("ok\n");
});
```

#### Timeout Tests

```typescript
it("should time out", async () => {
  // Don't send any response - let it time out
  await expect(
    client.command.eval("sleep 100", { timeout: 50 })
  ).rejects.toThrow(TimeoutError);
});
```

### Coverage Requirements

All new code must maintain **80% minimum coverage** across branches, functions,
lines, and statements. The CI pipeline enforces this threshold.

### Integration Tests

Integration tests in `tests/integration/` require a running bash-server.
They are skipped by default and run explicitly:

```bash
# Start a test server
bash-server --name jest-integration &

# Run integration tests
npx jest tests/integration/

# Clean up
kill %1
```

## Adding New Methods

To add a new method to an existing channel:

### 1. Define Types (if needed)

Add any new interfaces to `src/types.ts`:

```typescript
export interface NewResult {
  field1: string;
  field2: number;
}
```

### 2. Add the Method

In the appropriate channel file (`src/channels/state.ts`, etc.):

```typescript
async newMethod(arg: string): Promise<NewResult> {
  const response = await this.send({
    ch: CHAN_STATE,
    type: "new_operation",
    arg,
  });
  return {
    field1: response.field1 as string,
    field2: response.field2 as number,
  };
}
```

### 3. Write Tests

In the corresponding test file:

```typescript
describe("newMethod", () => {
  it("should return expected result", async () => {
    setTimeout(() => {
      mock.simulateData('{"ch":2,"type":"new_result","field1":"val","field2":42}\n');
    }, 10);

    const result = await client.state.newMethod("arg");
    expect(result.field1).toBe("val");
    expect(result.field2).toBe(42);
  });

  it("should throw on error response", async () => {
    setTimeout(() => {
      mock.simulateData('{"ch":2,"type":"error","error":"not found"}\n');
    }, 10);

    await expect(client.state.newMethod("arg")).rejects.toThrow(ServerError);
  });
});
```

### 4. Export (if new type)

Add the new interface to `src/index.ts` re-exports.

### 5. Document

Update `API.md` with the new method signature, parameters, returns, and examples.

## Adding New Transports

To add a new transport implementation:

### 1. Implement the Transport Interface

In `src/transport.ts`:

```typescript
export class NewTransport implements Transport {
  write(data: Buffer): void {
    // Write to underlying I/O
  }

  on(event: "data", handler: (chunk: Buffer) => void): void;
  on(event: "close", handler: () => void): void;
  on(event: "error", handler: (err: Error) => void): void;
  on(event: string, handler: Function): void {
    // Register event handler
  }

  async close(): Promise<void> {
    // Clean up resources
  }
}
```

### 2. Add Factory Method

In `src/client.ts`:

```typescript
static async connectNew(options: NewOptions): Promise<BashClient> {
  const transport = new NewTransport(options);
  await transport.connect();
  const client = new BashClient(transport);
  await client.authenticate(options.token);
  return client;
}
```

### 3. Write Tests

- Unit test the transport with mocked I/O.
- Integration test with a real bash-server using the new transport.

### 4. Document

- Update `GUIDE.md` with usage examples.
- Update `API.md` with the new factory method.
- Update `ARCHITECTURE.md` with the transport design.

## Adding New Channels

Adding a new channel is a larger change:

### 1. Define the Channel ID

In `src/types.ts`:

```typescript
export const CHAN_NEW = 6;
```

### 2. Create Channel Module

Create `src/channels/newchannel.ts`:

```typescript
import { CHAN_NEW, Message, NewResult } from "../types";

export class NewChannel {
  private send: (msg: Message, timeout?: number) => Promise<Message>;

  constructor(send: (msg: Message, timeout?: number) => Promise<Message>) {
    this.send = send;
  }

  async someOperation(): Promise<NewResult> {
    const response = await this.send({ ch: CHAN_NEW, type: "some_op" });
    return response as unknown as NewResult;
  }
}
```

### 3. Register in BashClient

In `src/client.ts`, add the channel as a property and register it in the
dispatch table.

### 4. Write Full Test Suite

Create `tests/channels/newchannel.test.ts` with tests for all methods.

### 5. Export and Document

Update `index.ts`, `API.md`, `GUIDE.md`, and `ARCHITECTURE.md`.

## Documentation Standards

### API Documentation

Every public method needs a JSDoc comment with:

- One-line description.
- `@param` for each parameter.
- `@returns` describing the return value.
- `@throws` for each error type that may be thrown.
- Code example for non-trivial methods.

### Markdown Files

- Use ATX-style headers (`#`, `##`, `###`).
- Include a table of contents for files over 200 lines.
- Use fenced code blocks with language tags (` ```typescript `).
- Use tables for structured data.
- Keep lines under 80 characters where practical.

### CHANGELOG.md

Follow [Keep a Changelog](https://keepachangelog.com/) format:

```markdown
## [0.2.0] - 2026-XX-XX

### Added
- New feature description.

### Changed
- Changed behavior description.

### Fixed
- Bug fix description.
```

## Pull Request Process

### Before Submitting

1. **All tests pass**: `npm test` exits cleanly.
2. **Type-check passes**: `npx tsc --noEmit` has no errors.
3. **Coverage maintained**: `npm run test:coverage` shows >= 80%.
4. **Build succeeds**: `npm run build` produces output without errors.
5. **Documentation updated**: API changes reflected in docs.
6. **CHANGELOG updated**: New entry for user-visible changes.

### PR Description

Include:

- **Summary**: What changed and why.
- **Testing**: How the change was tested.
- **Documentation**: What docs were updated.
- **Breaking changes**: Any API changes that affect consumers.

### Review Checklist

Reviewers will check:

- [ ] Types are correct and complete (no `any` casts without justification).
- [ ] Error handling is present for all failure modes.
- [ ] Tests cover the happy path and at least one error path.
- [ ] Public API changes are documented.
- [ ] No external dependencies introduced.
- [ ] Backward compatibility preserved (or breaking change is justified).

### Merge Requirements

- At least one approving review.
- All CI checks pass.
- No unresolved review comments.
